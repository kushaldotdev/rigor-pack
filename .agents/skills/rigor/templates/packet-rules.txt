1. PROJECT RULES: the PROJECT RULES block below (environment, secrets, containers, check commands)
   binds as much as these rules. Never open, print, grep or source any .env file.
2. FENCE: a fix needing a file outside "You may change" -> stop and report BEFORE committing it.
3. TEST FIRST, FROM THE ORACLE: the task's ORACLE section says what right looks like. Write its
   rows as tests that fail on the task base for the finding's reason, then the smallest fix. For a
   "today's behaviour" table the test is differential: each row's input, the output the base gives
   (recorded from a run on the base, never from reading the code), and the same output on your
   tip. An input shape the ORACLE does not list: add the row with the base's output from a run,
   keep the base's behaviour, and name the added rows in the report. Prove red on an extracted
   tree of the base (git archive), never by `git checkout <base> -- file` or `git restore` over
   your work. Mock only true I/O borders.
4. TRADE-OFFS: name every behaviour change beyond the fix, even ones you think are fine. A result
   that differs from an ORACLE row is not a trade-off: stop and report it (rule 10).
5. {delegate} Ask L0 rather than guess: the ADAPTER question call in this packet's PROJECT RULES
   hands a question to L0's agent ({l0}), which keeps working on what the question does not block;
   with no such call, ask at the report.
   NEVER end your turn while a child runs (a worker, a
   lens reviewer, the probe): ending it is your report. Wait in slices of 10 minutes or less,
   never an unbounded wait. After each slice handle what finished; on a timeout check each
   running child once, nudge or interrupt one whose output has not moved, append a progress-log
   line, wait again. A child with children of its own waits the same way.
   Report only when every child has finished.
6. SELF-REVIEW before the report, by the method in
   {rigor}/templates/self-review.txt (read it first), over task
   base..last commit AND every deliverable file the task names, committed or not, with these
   lenses: {lenses}. Before the first loop you yourself read each lens body in full: a child's
   read is not yours, and L0 checks your own session for it. {loop} Every lens is a read-only
   child started with the file this command writes for it, verbatim (its brief below, plus the
   task's ORACLE and, for standards + spec, this packet's ARCHITECTURE RULES section):
     node {rigor}/scripts/lens-brief.mjs --packet {packet} --out-dir {briefs}
   Later loops add `--loop <n> --since <previous loop's last commit> --lenses <lenses whose
   findings were fixed>`; a fix round after a review (rule 12) uses `--fix-round --since <the tip
   the review saw> --class <class>` (one --class per finding class); the final loop's probe uses
   `--probe`. The standards + spec child may start as soon as the code is
   committed, while the targeted tests and coverage still run. The loop-1 briefs:
{lens_briefs}
   Probe: {probe}
   Lens check: right after the loop-1 lens children are launched, run {lens_check}. A failing row
   means a child went out without its lens body: stop it and relaunch it from its brief file now.
   Start the self-review file before the first loop with
     node {rigor}/scripts/review-file.mjs --packet {packet} --init {cr}
   It writes one section per lens (no lens ranks another) and, at the end of the standards + spec
   section, this block, one line per item, each to be filled from a read or a run (the
   ARCHITECTURE RULES section of this packet is the checklist). No heading between that section's
   heading and the block may name a lens or the probe: one ends the section before the block:
     ARCHITECTURE
     - Deletion test: <each new or changed module>: <passes / fails, and why>
     - Duplicated owners: <a default, parse or decision now owned in two places, or none>
     - Shims left: <compatibility shims, re-exports, dead branches left behind, or none>
     - Single-implementation seams: <an interface, registry or option with one implementation, or none>
     - ADRs: <each ADR for the area, kept or contradicted, or none apply>
     - Lint/contract output: <the import-contract or lint command and its result line>
   Fix every act-on finding and list fixed / deferred / rejected with reasons. Mutants: {mutants}.
   Before you report, run
   `node {rigor}/scripts/review-file.mjs --packet {packet} {cr}` and report
   only when it exits 0. L0 checks that file has every lens above and the ARCHITECTURE block,
   reruns the lens check, and counts your child calls before accepting.
7. COMMITS on {branch} only, as often as useful: {commit_subject}, with a hyphen-bullet body
   starting with verbs and {commit_trailer}. Note the branch tip first: that is the task base
   ({base}). Never push, merge, touch the main branch or the tracker. Scratch output, probe files
   and throwaway copies go under {wt}/tmp/ only. Give a copy a dependency dir (node_modules, a
   venv) as a container volume mount, never a symlink: removing a link or file outside tmp/
   needs a permission prompt.
8. CHECKS: the PROJECT RULES check commands, then targeted tests: every test file you add or edit,
   the tests mirroring each changed module, and any test that imports or calls a symbol you
   changed (grep for it; a changed signature breaks callers outside your fence). Run the full
   suite only when the TASK line says so, once, on a commit whose self-review act-on list is
   empty, never on a commit you already know you will change. Commit the doc half in the same
   range. Before you report, run the out-of-fence pre-run over the tests outside your fence: every
   one that names a changed public symbol, and every one that mocks or patches a module you
   changed, whether or not it names a changed symbol (a `vi.mock("<module>")` or `patch("app.<module>")`
   names only the module). The command is {pre_run}; paste its output and each failing file.
9. PROGRESS LOG: append `HH:MM UTC | step | next | blocker or none` (date -u) to
   {wt}/tmp/l1-progress.log every 15 minutes and after every step. Wrap anything that can run over
   10 minutes in `timeout`. If the same step shows on 3 lines in a row, stop and report.
10. REPORT: base..last commit with subjects, test names, red output on the base, green on your
   last commit, check commands and counts, files changed, anything you started and removed,
   trade-offs, ORACLE rows you added, surprises. If a "Stop and ask L0 if" line fires, stop and
   report instead of guessing.
11. HISTORY: never `--amend` or rewrite history. Delete only scratch you created yourself. In a
   shared worktree (the TASK block names the other writer), run lint, format and fix commands on
   your own paths only, never repo-wide, and commit with `git commit -m ... -- <your paths>`.
12. FIX ROUND (any re-brief after a review): a finding is one case of a class. For each finding,
   name the class, list every site or input shape of that class in the code this task owns (from a
   grep or a run, pasted in the report), fix the whole list, and pin it with one test that walks
   the list. A round that fixes only the cited case comes back. Then run the checks (rule 8). The
   round's self-review is one loop aimed at the finding's class, not the whole of rule 6 again:
   standards + spec on the round's delta (`lens-brief.mjs --fix-round --class`), checking each
   class at every site in the task range, plus one probe on the class when this task gets a
   probe; no other lens runs again. Record it as a loop in the self-review file and rerun
   review-file.mjs before you report.
13. GUARD REACH: what a guard (scan, validator, lint, check) catches is stated once, in its own
   docstring, generated from its constants or pinned by a test against them. Other docs and
   comments cite that docstring and never restate or widen its reach. A universal word in a docs,
   docstring or comment line you add or change (every, only, always, never, one place, sole) is a
   claim about the whole repo: paste the grep behind it. Docs-claim command: {docs_claim}.
14. PROOF, NOT CONFIDENCE: a statement about the code in a packet or a plan ("X keeps its
   contract", "Y already locks first", "only Z reads it") is a claim to check, never a fact. Run the
   grep or the test that settles it before you build on it, and report it if it is wrong.
