SELF-REVIEW METHOD (packet rule 6 points here; the packet names your lenses, briefs and file)

LOOPS, AND WHAT EACH ONE SEES
- Loop 1: every lens the packet names, each over the whole range (task base..last commit, plus
  every deliverable). The standards + spec child may start as soon as the task's code is
  committed, while the worker still runs the targeted suite and coverage; the other lenses start
  together, in one parallel call.
- Loop 2 and later: only the fix commits since the previous loop (<the previous loop's last
  commit>..HEAD), with standards + spec plus each lens that raised a finding those commits fix.
  A lens with no finding fixed in the delta does not run again.
- Coverage invariant: every line of the range is seen by every required lens once, and every line
  changed afterwards is seen again. So a loop's range starts at the last commit the previous loop
  reviewed, never later, and a commit made while a loop runs belongs to the next loop's delta.
- The loops end when a loop's act-on list is empty and no commit landed after its range (a test
  fix made while the early standards + spec child ran is such a commit: the next loop's delta).
  Then comes the probe, if the task gets one.
- Loop cap: at most the loop cap the project's workflow settings set (default 3) per attempt,
  loop 1 included. A loop at the cap whose act-on list is not empty ends the loops anyway: fix
  what is quick in that loop's delta without a further lens loop, run the probe if due, and list
  every finding still unfixed under `## Open at cap` in the self-review file, each with its
  class, file:line and why it is open. The delegator rules each one in its own review; a report
  with that section is not a missing self-review.
- Log every loop in the file's Loops section: range, lenses, act-on count.

WHO RUNS A LENS
- Every lens is a read-only reviewer child: it reads, and runs nothing that writes. It is started
  with the file `lens-brief.mjs` writes for it (packet rule 6), verbatim, never with your own
  account of the lens.
- The same child across loops: send a later loop's delta brief to the child that ran that lens in
  the loop before, as a follow-up (your harness notes name the call and where its context size
  shows), while its context is under the lens-child ceiling the project's workflow settings set
  (default ~150k tokens). Past it, or when the harness cannot send a child a follow-up, start a
  fresh child with that lens's loop-1 brief file and then the delta brief, both verbatim. A lens
  child is never the child that wrote the task's code.
- The final loop (the read-only lenses came back with an empty act-on list): the packet says
  whether this task gets a probe. Only a hard or critical task that changes behaviour does. Then
  blast radius and interrogate run ONCE more, together, as one probe child: a child that can run
  commands (your harness's worker), never the child that wrote this task's code. It works only in
  a throwaway copy of your last commit under <worktree>/tmp/probe/, never in the worktree, and
  runs every attack itself. Where a lens body calls for several adversaries and the child cannot
  start children, it plays each adversary in turn. A refactor that keeps behaviour, and every easy
  or medium task, never gets a probe: its read-only lenses are the whole self-review.
- After the probe, a fix it causes gets a read-only delta review (a loop by the rules above),
  never a second probe.
- No child agents: run each lens yourself, in the packet's order, reading its body in full first,
  over the same ranges.
- With child agents you still read every lens body yourself before the first loop (packet rule 6).

FORM BY CONSTRUCTION (L0 runs both checks again)
- Start the self-review file with `review-file.mjs --init` (packet rule 6): it writes the
  headings and the ARCHITECTURE block where the check looks for them. Fill them in place; never
  rename or move a heading, and add no heading naming a lens or the probe inside the standards +
  spec section.
- Right after the loop-1 lens children are launched, run the project's lens check (packet rule
  6). A failing row means a child went out without its lens body: stop it and relaunch it from
  its brief file then, not after the report.
- Before the report, run `review-file.mjs` on the file. Report only on exit 0.

YOUR OWN RUNS, EVERY LOOP (paste each command and its output in the file)
- Deletions: for each symbol, file, flag or branch the loop's range deletes, grep its name across
  code, comments and docs. A comment or doc that still names it, or explains code that is gone,
  is a finding.
- Tests together: run every test file the range adds or touches in ONE test-runner call, as well
  as one by one. A test that passes alone and fails beside the others leaks state (a mock, patch,
  cache or fixture that outlives its test): a finding.
- Docs claims: every docs or docstring sentence the range adds or changes that states a rule's
  reach, order or owner cites the code line or test that proves it; one with no proof is a
  finding. Grep the repo for the claim's key wording and paste the grep: each other restatement
  it finds is checked the same way.

PROBE LIMITS (the probe brief repeats them; a probe over them is stopped and reported as partial)
- Time box: 15 minutes of attacks. Report what ran by then; list the rest as "not run".
- At most 5 attacks, chosen from the task's ORACLE rows by risk: the rows whose failure would
  cost most, first. A mutant table runs only when the ORACLE asks for one by name.
- Targeted test files only, each named by path. Never the whole suite: no test runner call
  without a test path (no bare `pytest`, `pytest tests`, `npm test`).
- Every command in the foreground, wrapped in `timeout`. No `sleep` polling, no waiting on a
  sibling's container or run.
- One container pair (or the project's one isolated environment) per probe, started by the
  probe, and removed before it reports.

WHAT EVERY CHILD GETS (the brief file lens-brief.mjs writes holds all of it)
- Its packet brief, verbatim, or the delta brief built from it; each names the lens body by path.
  A child briefed from your summary of a lens has not run it.
- The standards + spec child (and the probe) also gets the packet's ARCHITECTURE RULES section,
  verbatim: the skill text it quotes is the checklist, so the child needs no other file for it.
- The task's ORACLE section, verbatim; the probe also gets the PROJECT RULES section on running
  tests in isolation (it needs it to run anything).
- Never your account of what the change does. The child judges the work against the ORACLE and
  against what the task base does, not against your reading of the task.

WHAT IS IN SCOPE
- Loop 1: the range task base..last commit, and every deliverable file the task names, committed
  or not: an outcome or report under tmp/, a plan, a draft. A later loop or a fix round: its delta,
  and every deliverable the delta changes.
- Every consumer of a value, default or rule the change moves, in whatever module it lives. A
  consumer outside your fence is a finding to report, not to fix.

WHAT COUNTS AS A FINDING
- A probe child's finding carries the command it ran and the output. One with no run is listed as
  "unproven" and is not counted until a run shows it.
- Back every claim of changed behaviour and every worked number in the work or the report with a
  run: a scratch command in a throwaway copy, with the command and its output in the self-review
  file. For a claim of changed behaviour, a line citation alone does not count. A claim that a
  refactor keeps behaviour may stand on the cited lines plus the existing tests that cover them,
  each named. Rerun a claim a child disputes before you count or dismiss it.
- Name each finding's class, then look for its siblings before you fix (packet rule 12).

A FIX ROUND AFTER A REVIEW (packet rule 12: L0's review, or any re-brief with findings)
- One loop, aimed at the finding's class, not the whole method again. First fix the class
  everywhere in the task range (task base..HEAD), not only where the reviewer pointed: list every
  site or input shape from a grep or a run. Then run the check commands and the targeted tests.
- Then one standards + spec child on the round's delta, from `lens-brief.mjs --fix-round --since
  <the tip the review saw> --class <class>` (one --class per finding class): it checks each class
  is fixed at every site in the task range. When the packet gives this task a probe, one probe
  on those classes runs beside it, within the probe limits. No other lens runs again.
- That is the round's only loop. Fix what it finds in the same round without another lens loop,
  or list it under `## Open at cap`. Log the loop in the file and rerun `review-file.mjs` before
  the report. L0's own delta review follows as before.
- The reviewer re-reads every changed deliverable whole, not only the lines the findings name,
  and lists each claim the rewrite newly makes. Run each claim of changed behaviour.

THE FILE
- One section per lens; no lens ranks another. Per finding: class, proof (command and output, or
  for a refactor the cited lines and named tests), and fixed / deferred / rejected with the reason.
- The standards + spec section ends with the ARCHITECTURE block packet rule 6 lays out, with no
  heading naming a lens or the probe before it inside that section.
