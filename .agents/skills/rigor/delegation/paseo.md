# Paseo adapter

Maps each operation in [README.md](README.md) to Paseo's MCP tools or the `paseo` CLI. Paseo is the delegation tool when `docs/agents/workflow.md` → Chain efforts names it, and the file named there. Model ids and thinking levels are settings: take them from that section, never from here; the ids below are examples.

| Operation | Call | Result |
|---|---|---|
| create or reuse a workspace for a worktree | `create_workspace` with `{ isolation: "local", path: <worktree> }`; CLI `paseo workspace create --isolation local --path <worktree>` | A `workspaceId`. Reuse it for every task of that ticket |
| spawn an agent | `create_agent` with `{ workspaceId, provider: "<family>/<model id>", settings: { thinkingOptionId: "<level>" }, title: "<id> T<n> <task>", labels: { effort: "<slug>", ticket: "<id>" }, initialPrompt: <the packet>, notifyOnFinish: true }`. Example provider: `pi/some-model-id` at `max`; example reviewer: `codex/some-model-id` at `high` | `{ agentId, workspaceId }`. A finish notification arrives when its turn ends; the builder's packet also has it report by message (the row below) |
| start an L1 coordinator (no finish notice) | the same `create_agent` call with `notifyOnFinish: false`, `initialPrompt` = the L1 brief, and the L1's model and level from workflow.md's coordinator row | `{ agentId }`. L0 then builds the packet with that id (`--l1-id`) and sends it as the first follow-up; the L1 wakes L0 by message only |
| the builder's report to its L1 (the packet's standing order) | `paseo send --no-wait <L1 agent id> "done|question|blocked: <report path or question>"` as the last action of every turn | L1 wakes on the message even when the finish notice never fires; it answers a question through the same call |
| report, block or question from an L1 to L0 | `paseo send --no-wait <L0 agent id> "<report, blocked or question: ...>"` (`send_agent_prompt` with `{ agentId, prompt }` from code). The packet carries L1's id (`mkpacket.mjs --l1-id`); the L1 gets L0's id from its own launch | L0 reads it at its next step and answers through the same call; the L1 keeps working on what the question does not block. `contact_supervisor` is not this channel: it fails in a top-level session |
| send a follow-up | `send_agent_prompt` with `{ agentId, prompt: <the re-brief>, notifyOnFinish: true }`; CLI `paseo send <agent-id> "<prompt>"` | The same agent works again, with its history |
| get status, activity and context usage | `get_agent_status` for running or finished plus `lastUsage` (the context size); `get_agent_activity` for its recent steps | Status, last activity, context size to compare with workflow.md's ceiling |
| recover a lost finish notification | `get_agent_activity` on the `agentId` | Its last steps and final message |
| archive an agent | `archive_agent` with `{ agentId }` | Off the running list; transcript kept |
| archive a workspace and its leftovers | `archive_workspace` with `{ workspaceId }`, then `paseo project ls` and `paseo project delete <project-id>` for that worktree's project (see Gotchas) | Nothing of that ticket listed |
| create a recurring heartbeat to self | `create_heartbeat` with `{ cron: "<interval from workflow.md>", prompt: <the tick prompt>, name: "<slug> watch" }`; an L1 names its own `"<slug> T<n> tick"` | A heartbeat that prompts L0, or that L1, on that cadence. Neither sends a status report to L0 |
| delete the heartbeat | `delete_heartbeat` with `{ name }` or its id. There is no update tool: delete and recreate | No more pings; an L1 deletes its own tick when its task is accepted |
| start a top-level successor session with labels | `env -u PASEO_AGENT_ID paseo run --no-wait --new-workspace local --provider <family>/<model id> --mode bypassPermissions --cwd <the main checkout> --title "<slug> S<n+1>: <tickets>" --label effort=<slug> --label session=<n+1> "<briefing>"`, then `paseo workspace rename <new workspace id> "<slug> S<n+1>: <tickets>"` | A new top-level session in its own workspace on the same checkout; record the returned agent id in the trail's `next` row |
| list running sessions by label | `paseo ls -a --label effort=<slug>`, then read the STATUS column (see Gotchas); MCP `list_agents` with `{ cwd, statuses, includeBackground: true }` | The chain's live sessions, or none |
| count running agents against the caps | `list_agents` (running only) and `list_workspaces` with `includeBackground: true` | Running agents and open worktrees, to compare with the caps in workflow.md |
| model choice with no id given | `list_profiles` first, read every profile's `notes`, then materialize the matching one into `create_agent` (`provider` = `family/model`, plus its `settings`) | A provider and settings for any launch |

## Gotchas

- **Builders start through `create_agent` only.** `paseo run --no-wait` sets no finish notice, so an L1 never hears its builder finish. Launch with `create_agent` and `notifyOnFinish: true`; the builder's last action in every turn is still a `paseo send --no-wait` to its L1.
- **A worktree workspace leaves a project behind.** `create_workspace` on a worktree path also registers a project, which `archive_workspace` leaves in place. At landing, archive the workspace **and** run `paseo project delete <id>` for it, once `paseo project ls` shows the worktree path.
- **Never delete the main checkout's project.** `create_workspace` on the main path returns the main project id, and deleting it once killed the lead session. At session start and close, list workspaces and projects with `includeBackground: true`; clean only those whose ticket landed.
- **The successor must be top-level.** `env -u PASEO_AGENT_ID` before `paseo run` keeps the new session out of the closing session's parentage, so it survives that session's archive; `--no-wait` returns at once. Without `--new-workspace local`, a `paseo run` from an agent-scoped caller lands in the caller's workspace; with it, the successor gets its own workspace on the same checkout. Rename that new workspace, never the caller's, at once: `paseo run` names it after the branch.
- **Plain `paseo ls` hides background agents.** A child started in the background (a pi builder, say) shows only with `-a` (or `--background`), so `paseo ls --label effort=<slug>` can print nothing while one runs. List with `-a` and count the `running` STATUS rows; archived and closed agents do not count.
- **`notifyOnFinish` means do not poll.** Finish the turn and wait for the notification; poll only when one is already lost, and recover it from `get_agent_activity`. Every launch takes it but an L1's: an L1 ends its turn right after launching its builder, and `paseo send` from the builder (the standing order in its packet) is what wakes it. An L1 that a tick finds idle may be holding a question: answer it in that turn.
- **A rule change is a steer, not a new task.** Send the rule text or its path through `send_agent_prompt` (or `paseo send`) to every running agent it binds, saying it binds their next report; never a "leave in-flight work as it is" relay (CHAIN.md → Talking to the owner).
  - **`send_agent_prompt` revives agents after a reboot.** The agent keeps its history; rerun any background suite that died with the host.
- **Context size is `get_agent_status` → `lastUsage`.** Compare it with workflow.md's ceiling and start a fresh agent past it.
- **Heartbeats have no update.** `create_heartbeat` and `delete_heartbeat` only; change the cadence by deleting and recreating.
- **`list_profiles` first.** When no model is named, read the profiles' notes before choosing a provider and thinking level.
